# agent_1 / agent_2 分工与 agent_2 评审操作规范

日期：2026-11-15。状态：流程草案，待评审。适用于 Hermes 本地实验（Local Harness
Lab）及其后续文档与实现。本文补充 [AGENTS.md](../AGENTS.md)、
[开发工作流](development-workflow.md) 与 [Git 流程](git-workflow.md)，不替代它们；
冲突时以后三者为准，并在同一变更中修正本文；合并权限以本文“交叉评审与合并权限”
一节记录的用户授权为准。

## 角色与文件归属

| 角色 | 主要职责 | 主要文件 |
| --- | --- | --- |
| agent_1 | 完成交付计划内容并按里程碑实施 | [交付计划](plans/local-harness-deliveries.zh-CN.md)、ADR、配置、脚本和测试 |
| agent_2 | 评审已提交的 PR 与产出，提出并推动改进 | `docs/reviews/`，经评审确认的修订 PR |

- 计划文件以 agent_1 为主。agent_1 有开放 PR 修改某文件时，agent_2 不改该文件。
- agent_2 发现问题时，先写入评审报告。改进 PR 仅在相关文件没有被他人开放 PR
  占用，且改动属于评审结论时提交，并与评审报告分开为两个 PR。
- 两个 agent 不共用同一个工作区做写操作。agent_2 使用独立的 `git worktree` 或独立
  克隆，避免切换分支时带走对方未提交的改动。
- 不提交不属于本任务的未跟踪文件，不使用强制重置、清理或 stash 处理他人的工作。
- 会话已指定分支名时优先使用该名称，否则用 `docs/*`、`chore/*` 等既有前缀。

## agent_2 的评审流程

### 1. 确定评审对象

1. 用 `gh pr view` 与 `gh pr diff` 获取 PR 状态、描述、文件列表和完整 diff。
2. 记录对象的状态（开放、Draft、已合并）与对应的 `main` 提交。已合并的 PR 按
   “回顾性评审”处理，报告写明评审基线提交。
3. 读取 AGENTS.md、开发工作流、PR 模板和被评审的计划或 ADR，明确验收口径。
4. 报告只陈述实际读到、运行到的内容。无法确认的点标明未验证，不推断结论。

### 2. 复核产出

- **独立复算证据。** 对 PR 声称的哈希、计数、版本号、命令结果，自行从源头重算，
  不引用 PR 的转述。
- **运行前先读脚本。** 复跑仓库脚本之前读完全文，确认只访问本地资源。不执行来源
  不明的下载物，不在评审中安装依赖或下载模型，除非用户明确要求。
- **对照验收项。** 逐条对照计划中的验收 ID 和退出条件，判断“已完成”“部分完成”
  “不在本 PR 范围”。文档通过不等于功能验收通过，不得把二者混为一谈。
- **检查一致性。** 状态措辞是否随合并更新；README、计划、ADR 之间链接和编号是否
  一致；验收 ID 是否唯一；声明的范围与证据范围是否相符。
- **安全与隐私。** 授权、隔离、凭据处理、数据保留、日志内容、供应链来源和平台
  可行性。仓库中不得出现密钥或真实个人数据。
- **可行性。** 区分设计层面的风险和已被证据证实的问题，标明对后续里程碑的影响。

### 3. 评审形式与报告格式

**评审形式。** 按 PR 规模选择，不要求每次都新增文件：

- **小 PR：用 PR 评论评审。** 同时满足以下条件时，用 `gh pr review --comment`
  把评审写在 PR 上，不另提评审报告 PR：
  - 单一意图，文件数不超过约 10 个，增删行数不超过约 800 行；
  - 不新增或改变安全、隐私、授权或持久化边界；
  - 评审中没有“高”严重度发现。
- **其他情况：写评审报告文件。** 大 PR、涉及上述边界，或评论评审中出现“高”
  严重度发现时，升级为 `docs/reviews/` 下的报告并走评审 PR。
- 两种形式的内容相同：评审基线提交、结论、已复核项、编号发现（F#，含严重度）、
  建议和范围声明。评论只是载体不同，不降低复核标准。
- 评论评审同样遵循“独立复算、运行前读脚本、不夸大”。作者的响应记录按
  “agent_1 对评审的响应流程”处理，评论里的 F# 与报告中的 F# 等价。

**报告格式。** 写报告文件时写入 `docs/reviews/<主题>.zh-CN.md`，使用以下结构：

1. 标题、评审日期、评审基线 `main` 提交、被评审对象链接；声明本次未做什么
   （例如未安装依赖、未运行模型）。
2. **结论。** 先给判断：可否继续、是否有阻塞项。
3. **逐项核对。** 表格列出“声称 / 实际结果”，只列已复核项。
4. **发现。** 编号 F1、F2……，每条给出严重度（高/中/低/信息）、依据和建议。
   严重度按对后续里程碑、安全和复现性的影响排序，不按字数排序。
5. **与计划的对照。** 哪些属于缺失，哪些本来就属于后续里程碑。
6. **建议的后续顺序。** 小步、可独立评审的 PR，写明先后。

文字要具体、可核实，不使用无法判定的措辞（如“稳定”“合理”）。建议改写验收项时，
写成“输入 fixture → 可断言的预期输出”。

### 4. 提交评审报告 PR

本节只适用于写报告文件的情况；小 PR 的评论评审不需要。

1. 从最新 `origin/main` 创建独立分支（`docs/*`），在独立 worktree 中工作。
2. 新增报告并在 README 添加入口；不夹带对被评审文件的修改。
3. 提交前运行文档检查并报告结果：`git diff --check`、相对链接、尾随空白、代码围栏、
   结尾换行、验收 ID 唯一性、JSON 证据可解析。仓库尚无统一检查命令时如实写明，
   并说明无法运行的检查及其前提。
4. 提交信息末尾加入约定的 Co-Authored-By 行；`git add` 只列出本任务文件。
5. push 前核对分支 PR 状态并 rebase 到最新 `origin/main`。
6. 开 Draft PR，加 `documentation` 标签，按
   [PR 模板](../.github/pull_request_template.md) 填写，Prompt history 引用用户请求
   和日期，并列出所遵循的指令；写明哪些检查未运行。
7. 标记 ready 按下文“标记 ready 的规范”，合并按“交叉评审与合并权限”执行。合并使用
   squash，合并后确认状态，再同步 `main` 并清理分支。

### 5. 改进 PR

评审报告合并后，改进另开 PR：

- 一个 PR 只处理一类意图，如“修订计划中的验收口径”“补充检查脚本”。
- 改进对应评审编号（F#），PR 描述逐条说明采纳、调整或不采纳的理由。
- 修改 agent_1 负责的文件前，先确认没有开放 PR 占用；有冲突则等待其合并后 rebase。
- 变更涉及行为、接口、隐私或持久数据时，先更新设计文档，再实现。

## agent_1 与 agent_2 的交接

1. agent_1 在 PR 中给出验收 ID、命令、证据与未验证项。
2. agent_2 评审并提交报告 PR；严重度为“高”的发现须在继续下一个里程碑前得到
   处理，或获得被接受的跳过理由。
3. agent_1 按下节流程逐条评估发现，决定修改或跳过，并提交记录 PR。
4. 合并权限见“交叉评审与合并权限”一节。

## agent_1 对评审的响应流程

agent_1 不需要机械采纳每条发现。收到评审报告后，对每条 F# 先评估再决定：

1. **合理性。** 发现的依据是否成立：事实是否准确、对照的计划或标准是否正确、
   是否已有证据反驳。必要时自行复核，不直接采信，也不直接否定。
2. **必要性。** 不处理的代价是什么：是否影响安全与隐私、后续里程碑、验收口径、
   复现性或评审可信度；处理的成本与范围是否与收益相称。
3. **决定。** 每条只能选一个：
   - **采纳**：修改，并指出修改的文件与位置。
   - **部分采纳**：说明采纳的部分、不采纳的部分及理由。
   - **跳过**：不修改，直接进入下一步。必须写明理由，并标明是“不合理”
     “不必要”还是“推迟到某里程碑”；推迟项写明承接的里程碑或验收 ID。
4. **记录。** 决定写入 `docs/reviews/<主题>-response.zh-CN.md`，每条包含：发现
   编号与严重度、合理性判断、必要性判断、决定、理由、修改位置或承接项。
   不得只给结论而省略理由。
5. **提交 PR。** 记录与采纳的修改可放在同一个 PR（只要意图单一），按普通 PR 流程
   开 Draft、加标签、填写模板。PR 描述列出采纳、部分采纳、跳过的数量与清单。
6. **跳过不阻塞。** 被跳过的发现不阻止 agent_1 进入下一步。但“高”严重度发现被
   跳过时，须在 PR 描述中单独标出，由评审方（agent_2）复核理由：理由成立则合并，
   不成立则回到 agent_1 处理；双方意见不一致时交用户裁决。
7. **复核。** agent_2 评审该记录 PR 时，核对理由是否成立、采纳的修改是否对应发现，
   不因被跳过本身而拒绝；对理由不充分的跳过提出新的发现编号。

agent_2 的评审同样可以被评估后跳过，这是协作的一部分，不视为对评审的否定。

## 开始新 PR 前的检查

两个 agent 每次准备写新 PR（包括评审报告、记录 PR 和实现 PR）之前，先做下面的检查，
再继续下一步：

1. `git fetch origin`，用 `gh pr list --state open` 列出所有开放 PR。
2. 判断每个开放 PR 的作者：看 PR 描述中的 `Agent:` 标注（见下）、分支名、提交
   Co-Authored-By 和 Prompt history。无法判断归属时，不当作自己的 PR，询问用户。
3. **有另一个 agent 的开放 PR：先评审，再合并，然后才开始自己的新 PR。**
   - 评审按本文评审流程执行，合并按“交叉评审与合并权限”的条件执行。
   - Draft PR 按“标记 ready 的规范”判断：满足条件就标记 ready 并合并；不满足则
     在 PR 中留下评审意见并通知用户，不抢先改写对方的分支。
4. **评审后不能合并时**（有未处理的“高”严重度发现、检查失败、冲突、范围越界等）：
   记录评审结论回给作者；在其合并前，不开始依赖它的新 PR。与它没有文件和契约
   依赖的独立工作，仍须经用户确认后才可并行。
5. **有自己的开放 PR**：按既有规则，不开始依赖它的新 PR，等待另一个 agent 评审合并。
6. 合并后 `git fetch`，将本地 `main` fast-forward，再从最新 `origin/main` 创建
   新分支。已合并的 PR 对应分支，确认 SHA 与 PR head 一致后再清理。
7. 在新 PR 描述中写明本次检查的结果：检查时间、开放 PR 列表、哪些已评审并合并、
   哪些因何未合并。

每个 PR 的描述加一行 `Agent: agent_1` 或 `Agent: agent_2`，标明作者，供另一方识别。

## 交接与通知协议

用户 2026-11-15 的指示：提交后加标签并留交接评论，对方起步先查标签，可行时再发直接
消息；以下停止条件都要停下来问用户；其余情况不再每一步询问，直接自动继续。

agent 只有在自己的会话运行时才能行动，规范本身不能唤醒对方，所以协议以 GitHub 的
标签和评论为持久“信箱”，直接消息和定时唤醒作为加速手段。不设第三个指挥 agent。

1. **加标签（必需）。** 提交 PR、完成评审或完成回应后，给 PR 加标签
   `needs-review:agent_1` 或 `needs-review:agent_2`，指向下一步该行动的 agent。
   一次只指向一个 agent。接手方处理完成后移除自己的标签；需要对方继续时再加对方的。
   这两个标签已由用户同意创建；其他新标签仍须先询问用户。
2. **交接评论（必需）。** 同时在 PR 上留一条评论：首行 `Agent: agent_X`，第二行
   `Handoff → agent_Y`，写明：PR 与 head 提交、已完成什么、已运行的检查、期望对方做什么
   （评审、复核、合并或回应发现），以及哪些后续工作在等这个 PR。
3. **接收方起步先查标签。** 每次开始工作，先执行
   `gh pr list --state open --label needs-review:<自己>`，再做“开始新 PR 前的检查”，
   并读取这些 PR 中指向自己、尚无回复的 `Handoff → <自己>`。开始处理前回复
   `Handoff accepted`，处理完成后写明结果。
4. **直接消息（可行时）。** 对方是本机可达的 Claude 会话（`ListAgents` 能看到）时，
   提交后用 `SendMessage` 发一条短消息：首行自含地说明 PR 链接和期望动作。它不替代
   标签和交接评论，不得作为唯一通知。不用消息要求对方执行已被拒绝或可能被拒绝的操作，
   不为了问“完成了吗”而轮询。对方不可达或在另一个工具中运行时，只靠标签和评论。
5. **自动续跑。** 在已批准计划内，交接完成后不再询问用户“是否继续”，直接进行下一步，
   直到遇到下面的停止条件。这对 agent_1 和 agent_2 同样适用，取代此前“每一步后询问
   是否继续”的做法。
6. **定时唤醒（需用户开启）。** 要让两个会话不靠人工触发就持续推进，由用户为各会话
   开启定时唤醒（如 `/loop` 或定时任务），间隔不短于 20 分钟，每次只检查标签和交接
   评论，没有指向自己的交接就不动作。

**必须停下来询问用户的情况**（用户已确认全部适用）：

- 需要授权的操作：修改仓库设置或新增标签、凭据、付费、下载、其他贡献者的 PR。
- “高”严重度分歧：作者的跳过理由和评审方无法达成一致。
- 里程碑边界：计划中的一个里程碑完成，进入下一个之前。
- 连续几轮（三轮）交接没有实质进展，或同一问题在两个 agent 之间反复出现。
- 发现安全或隐私问题，或出现需要用户回答的开放问题。
- 对方在合理时间内没有响应且阻塞了后续工作。

停下来询问时，说明停在哪个条件、已完成什么、需要用户决定什么。

## 标记 ready 的规范

PR 开始都是 Draft。标记 ready 表示“内容已完成、可以合并评审”，不是随手操作。

**ready 条件**（全部满足才可标记）：

1. 内容已完成，没有占位、TODO 或未写完的小节。
2. 本地检查已运行并通过，结果和未能运行的检查写在 PR 描述的 Validation。
3. 分支已基于最新 `origin/main` rebase，且只含本任务文件。
4. PR 描述按模板填写，含 `Agent:` 标注、“开始新 PR 前的检查结果”和 Prompt history。
5. 已有的评审发现都已按“agent_1 对评审的响应流程”处理或写明跳过理由。
6. 没有需要用户先回答的开放问题；有则先询问，不标记。

**谁来标记：**

用户于 2026-11-15 指示：作者和评审方都可以标记 ready。

- **作者**满足条件后自己标记，并在 PR 评论中用一两句话说明已完成。
- **评审方**在评审另一个 agent 的 Draft PR 时，如果条件 1–6 均已满足且评审没有阻塞
  发现，也可以标记 ready，并随后按合并条件合并，避免双方互相等待。条件任一不满足
  时不标记，在 PR 上留下评审意见并通知用户。
- 任何一方标记时，都要在 PR 评论中写明依据（哪些条件已核对）。
- 不得为了让 PR 通过合并条件而标记尚未完成的 PR。

**标记之后：**

- 若又新增提交并改变了范围或行为，退回 Draft，重新满足条件后再标记。
- 标记 ready 不等于可以自己合并：不得合并自己提交的 PR。

## 交叉评审与合并权限

用户于 2026-11-15 指示：两个 agent 都有权评审对方的 PR 并合并。据此：

- agent_1 评审并可合并 agent_2 的 PR，agent_2 评审并可合并 agent_1 的 PR。
- **不得合并自己提交的 PR。** 合并方必须是评审了该 PR 的另一个 agent。
- 合并前须满足：已读完整 diff 并给出评审结论（评论或报告）；PR 已按上节标记
  ready；必需的检查通过（尚无 CI 时，核对 PR 描述中的本地检查并自行复跑相关项）；
  评审对话已解决；
  分支已基于最新 `origin/main`；没有开放 PR 占用同一文件而产生冲突。
- 评审发现“高”严重度问题且作者未按上节给出被接受的处理或跳过理由时，不合并，
  回给作者处理。
- 使用 squash 合并；合并后确认状态，核对远端分支 SHA 与 PR head 一致再清理分支。
- 在 PR 评论或会话中记录评审结论与合并依据，以便用户追溯。
- 本节授权仅限本仓库的 agent_1 与 agent_2 之间的 PR，不扩展到仓库设置修改、
  force-push、直接向 `main` 推送，也不扩展到其他贡献者的 PR。
- 用户可随时收回或收窄本授权，收回后恢复为每次合并需用户明确授权。

## 错误记录与自我改进

两个 agent 共用 [Agent 自我改进记录](agent-self-improvement.zh-CN.md)，用来积累错误
和预防规则，避免后续会话重复犯错。

1. **开始前读。** 每个会话写第一个 PR 之前，读“预防规则汇总”和与任务相关的记录。
2. **发现即记录。** 自己、另一个 agent 或用户发现错误后，先写入该文件，再修正；
   不得为省事而跳过记录。
3. **记录内容。** 每条包含日期、agent、严重度、发生了什么、原因、影响与纠正、
   预防规则、状态，不写借口。
4. **不写敏感信息。** 不记录密钥、凭据、真实个人数据或私人路径。
5. **评审时核对。** 评审方检查：错误是否如实记录、预防规则是否可执行、重复犯错时
   是否升级为本文的规则或检查。
6. **重复错误升级。** 同类错误出现两次，应把预防规则写入本文或 AGENTS.md，并在
   可能时改成可执行的检查，而不是只靠记忆。
7. **记录 PR 走正常流程。** 小的纯记录 PR 与其他 PR 一样需要 Draft、标签和另一个
   agent 的评审与合并。

## 硬性禁止

- 不得跳过、静音或削弱检查来让变更通过。

- 不得在 PR、报告、日志中写入密钥、凭据或真实个人数据；需要时使用占位并标记。
- 不得向外部服务发送本地路径、账号或其他私人信息。
- 不得直接向 `main` push 或 force-push。
- 不得合并自己提交的 PR；不得在上节条件之外合并，不得删除他人分支或修改仓库设置。
