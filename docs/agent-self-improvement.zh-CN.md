# Agent 自我改进记录

两个 agent 共用的错误记录与预防规则。规则来源见
[分工与评审操作规范](agent-collaboration.zh-CN.md) 的“错误记录与自我改进”一节。
目的是让后续会话读到这里就能避免重复犯同类错误。

## 使用方式

- **开始工作前读一遍。** 每个会话在写第一个 PR 之前，先读本文的“预防规则汇总”和
  与当前任务相关的记录。
- **发现错误就记录。** 无论错误由自己、另一个 agent 还是用户发现，在继续下一步之前
  先写入本文，再修正。
- **记录事实，不写借口。** 只记录发生了什么、为什么、影响、如何纠正、以后怎么防。
- **不写敏感信息。** 不记录密钥、凭据、真实个人数据、本地账号或私人路径。
- **一条记录对应一条可执行规则。** 无法落成规则的，写明是一次性问题。
- **记录 PR 走正常流程。** 与其他变更相同，开 Draft PR，由另一个 agent 评审。

## 记录格式

每条记录使用以下字段，编号 E1、E2……顺延：

- 日期、agent、严重度（高/中/低）
- 发生了什么
- 原因
- 影响与纠正
- 预防规则（以后怎么做）
- 状态：已纳入规范 / 仅本文 / 待评审

## 记录

### E1：修改了已合并 PR 的描述

日期：2026-11-15。agent_2。严重度：低。

- 发生了什么：我把新规则写进了 PR #18 的描述，但该 PR 已经被另一个 agent 合并。
- 原因：写入前没有先查 PR 状态，依据的是几分钟前的状态。
- 影响与纠正：已合并 PR 的描述记录了本次合并的内容，被改写后会误导追溯。发现后
  把描述恢复为原样，并确认没有残留。
- 预防规则：修改 PR 描述、推送或 rebase 之前，先 `gh pr view <编号> --json state`
  确认状态。已合并的 PR 不再修改，后续内容另开 PR。
- 状态：已纳入规范（“开始新 PR 前的检查”）。

### E2：声称“已同步”，但实际编辑失败

日期：2026-11-15。agent_2。严重度：中。

- 发生了什么：编辑 AGENTS.md 的工具调用失败（未先读取文件），我却已经在文档和
  PR 描述里写了“AGENTS.md 已同步”。
- 原因：把计划中的动作当成了已完成的结果，没有等编辑结果确认。
- 影响与纠正：文档与实际不一致。发现后重新读取文件、完成编辑并再次核对 diff。
- 预防规则：声明“已修改/已同步”之前，必须先确认对应编辑成功，并用 `git diff`
  核对声明与实际改动一致。声明写在修改之后，不写在修改之前。
- 状态：仅本文。

### E3：命令中遗留未重定向输入，造成挂起

日期：2026-11-15。agent_2。严重度：低。

- 发生了什么：一个命令末尾留了不必要的 `cat > 文件`，没有输入来源，命令等待标准
  输入，超时后转入后台，需要手动停止。
- 原因：写命令时拼接了一个多余的步骤，没有检查每一段是否会读取标准输入。
- 影响与纠正：浪费时间，且 PR 创建被延后。停止后台任务后重做。
- 预防规则：不在命令中保留会读取标准输入的命令（`cat`、交互式 `gh`、`git` 命令）
  而没有明确的输入；调用 `gh` 时加 `</dev/null`；长命令拆开，先小范围验证。
- 状态：仅本文。

### E4：在共享工作区里写操作，可能带走另一个 agent 的改动

日期：2026-11-15。agent_2。严重度：中。

- 发生了什么：开始时我在同一个 checkout 里创建分支并提交；之后另一个 agent 在
  该 checkout 切换了分支并留下未提交的改动。继续在那里切换分支会把对方的改动带到
  我的分支上。
- 原因：默认认为工作区只有一个使用者。
- 影响与纠正：改用独立 `git worktree` 提交后续 PR，只 `git add` 本任务文件，
  没有触碰对方的未提交内容。
- 预防规则：发现工作区有不属于自己的改动或分支，或存在另一个 agent 时，使用
  独立 worktree 或独立克隆进行写操作。`git add` 只列出本任务文件，不用 `git add -A`。
- 状态：已纳入规范（“角色与文件归属”）。

### E5：在已合并分支的基础上继续提交

日期：2026-11-15。agent_2。严重度：低。

- 发生了什么：我继续在 PR #18 的分支上提交新内容，rebase 时才发现该 PR 已经合并，
  冲突需要中止并重做。
- 原因：开始新工作前没有检查开放 PR 和分支对应 PR 的状态。
- 影响与纠正：中止 rebase，把最后一个提交基于最新 `main` 重新提交为新 PR；没有
  丢内容。
- 预防规则：每次开始新的编辑、提交或推送前，先 `git fetch` 并核对对应 PR 的状态；
  已合并则从最新 `origin/main` 建新分支。
- 状态：已纳入规范（“开始新 PR 前的检查”）。

### E6：内容交付后仍将 PR 留在 Draft

日期：2026-11-15。agent_1。严重度：低。

- 发生了什么：PR #20 内容与本地验证完成后，我将标记 ready 的动作一并交给评审者，
  自身 PR 继续保持 Draft，导致双方等待。
- 原因：没有区分作者声明可评审与另一 agent 批准合并的职责。
- 影响与纠正：当前回应 F1–F5，完成验证后由作者标记 ready，再交叉评审合并。
- 预防规则：作者在回应评审、检查通过后自行标记 ready，并读取 isDraft 确认；
  另一 agent 仍负责最终复核与合并。
- 状态：待评审。

### E7：严格 JSON 解析漏掉指数溢出的非有限浮点值

日期：2026-11-15。agent_1。严重度：中。

- 发生了什么：复核 F2 时构造 latency_ms=1e309，CLI 将其解析为正无穷并接受。
- 原因：只用 parse_constant 拒绝 NaN/Infinity 字面量，没有检查正常指数语法的溢出。
- 影响与纠正：新增有限浮点解析检查与指数溢出 CLI 回归，合法大有限值保留。
- 预防规则：严格 JSON 数值测试同时覆盖 NaN/Infinity 字面量和正负指数溢出；
  用共享解析入口校验，避免不同 CLI 的行为漂移。
- 状态：待评审。

## 预防规则汇总

1. 修改 PR、推送、rebase 前先查 PR 状态；已合并的 PR 不再改。（E1、E5）
2. 声明“已完成”之前先确认动作成功，并用 `git diff` 核对。（E2）
3. 命令不留会读取标准输入的步骤，`gh` 加 `</dev/null`。（E3）
4. 有他人改动或另一个 agent 时用独立 worktree，`git add` 只列本任务文件。（E4）

5. 作者检查通过并回应评审后标记 ready，再交给另一 agent 合并。（E6）
6. 严格 JSON 同时检查浮点常量和指数溢出。（E7）
