# PR #10 评审与改进建议

评审日期：2026-11-15。基于 main `0b5002a`，对照已合并的
[PR #10](https://github.com/jolearningusa/agent-os/pull/10) 及其交付计划
[Hermes 本地实验交付物与里程碑](../plans/local-harness-deliveries.zh-CN.md)。
本文是文档层面的复核，只读取了 PR #10 的变更，没有运行任何 Hermes、Ollama 或
实现代码。本文提出建议，不修改原计划，不新增外部事实断言；建议采纳前需先经评审，
并在对应实施 PR 中同步修订计划与 ADR。

## 总体判断

PR #10 可以保留，没有阻塞项。范围单一，层次清楚（L0 契约、L1 启动、L2 接模型、
L3 采集、L4 查看、L5 基线），拟定接口和待定项均已标注，27 个验收 ID 与 PR 描述
一致。下列问题集中在风险排序、范围粒度、验收可判定性和安全落地机制。

## 发现与建议

编号 F1–F10，按优先级排序。

### F1：核心风险验证过晚，高优先级

实验价值取决于 Hermes 能否在组装层和发送边界采集上下文（L3），但计划只在 L0 的
L02 确认“采集位置”，L1/L2 完成后才真正实现采集。若固定版本没有可用挂点，需要
修改 fork 核心，前面的启动与接入工作可能返工。

建议：把 L02 升级为采集可行性探针，用 mock 端点抓取一次完整请求，并在 ADR 中写明
go/no-go 判据与失败时的回退（更换版本、适配层包装或缩小范围）。

### F2：L0 范围过载

L0 同时包含 ADR、fork 归属、许可证、硬件盘点、模型选择、配置 schema、事件契约、
探针、`make check` 与 CI，却只有 L00–L03 四项验收。CI 和事件契约没有对应验收，
也与“每个 PR 一项能力”的约束冲突。

建议：拆为 L0a（ADR、fork、许可证、实施顺序、保留期限）与 L0b（schema、检查入口、
CI、探针）；为 CI、`make check` 和事件契约各增加验收项。

### F3：里程碑缺少规模与时间估计

计划只给出顺序，“决定后安排工期”。里程碑没有粗略人日、风险等级或依赖前置。

建议：每层补充粗略工作量区间与主要风险，并标明 L0 之前不承诺日期。

### F4：部分验收标准无法客观判定

- L20“必要历史”没有定义。
- L13“实例隔离”未说明隔离的是目录、端口、状态文件还是进程。
- L40、L41“核对所有字段”没有字段清单。
- 各层退出条件使用“稳定”“可以解释”等主观措辞。

建议：每项改写为“固定输入 fixture → 可断言的预期输出”，并列出字段清单。

### F5：安全措施缺少强制机制

- “关闭工具的网络和文件访问”没有说明执行手段。仅靠配置项可被工具绕过，应指定
  沙箱、容器或 allowlist。
- L23 要排除云端 fallback，但没有给出方法。建议在测试环境封锁出站网络，使云端调用
  必然失败，再断言仍能完成。
- L43 只覆盖本地会话鉴权与跨域，没有 Host 头校验（防 DNS rebinding）和 CSRF 防护。
- “访问控制”“保留期限”被推迟到 L0，应作为 L03 的必填产出，而不是可选项。

### F6：Fork 与供应链治理缺失

计划固定 commit，但没有说明上游安全补丁的跟踪与 rebase 节奏、本地补丁的隔离方式、
依赖哈希校验，以及安装阶段联网下载与“本地实验”定位的边界。

建议：ADR 增加上游同步策略、补丁清单规则、锁文件含哈希，并区分“安装期联网”和
“运行期仅本地”。

### F7：事件数据缺少版本与兼容策略

D5 事件被查看器和基线共同依赖，但没有 `schema_version`，文档仅泛称“需兼容读取或
迁移”。

建议：事件和导出包含 `schema_version`；规定向前兼容读取、不兼容变更时的迁移或拒绝
读取行为，并为此增加验收项。

### F8：Ollama 与 Token 统计的隐性行为

- 超出上下文窗口时服务可能截断输入。L22 提到截断，但应明确对比“发送的内容大小”
  与响应的 prompt 用量，以检出静默截断。
- 本地 Token 估算未说明所用 tokenizer，也未说明与提供方 usage 的误差如何记录。

### F9：文档自身一致性

- 计划状态写“提案，等待评审”，但 PR 已合并；应说明“已合并，内容待评审接受”，避免
  被误读为已确认。
- 里程碑名 L0–L5 与验收 ID L00–L53 前缀相近，L5 与 L50 易混淆；建议在文档加说明或
  改 ID 格式（如 `A-L0-01`）。
- L32 的“并发 session”与“单机、单用户”需说明指同一用户的多个 session。

### F10：文档验证不可复现

PR #10 的验证依赖一次性 Python 脚本，未入库，每个文档 PR 都需重写，CI 也无法复现。

建议：把文档检查（唯一验收 ID、相对链接、尾随空白、代码围栏）提交为仓库内脚本，
并在 L0b 的 `make check` 中接入。

## 建议的后续顺序

1. 一个 `docs/*` PR 修订原计划，处理 F1、F2、F4、F5、F9。仅涉及文档，风险最低。
2. 一个 `chore/*` PR 提交文档检查脚本并接入检查入口（F10）。
3. L0 ADR 先回答医疗 M0 顺序、fork 归属和保留期限，再处理 F3、F6、F7、F8。

本文不关闭任何验收项；所有建议待评审后再落地。
