## 评审方法与证据

1. 通读仓库当前 `main` 全部设计与流程文档（无应用实现代码）。
2. 对照外部公开资料核对关键假设：
   - OpenClaw：单 Gateway = 单信任边界，不支持互不信任多租户共用；插件有
     `before_channel_ingress` / `before_agent_run` / `before_tool_call` 等钩子，
     遥测默认排除原文，但**不能**替代项目自有 Privacy Gateway 与租户隔离。
   - Hermes：记忆/技能学习是上下文与程序学习，不是权重训练；进程内扫描不是
     对抗模型的最终边界。
   - RRSI：研究代码，适合离线 harness 优化；必须有留出集、安全门与人工审核。
   - Agno AgentOS：可作为能力清单参考；命名与本仓库重叠，避免对外混淆。
   - DeepSeek Harness：生命周期与模型流式契约文档存在，适合作为调用控制点参考。
   - PMC Open Access / NCBI API：可作为许可受限的文献连接器起点。
3. 按“原则对齐 → 产品边界 → 工程可落地性 → 风险与前置条件”评分。

本次仅文档评审，未运行应用测试；仓库尚无 `make check` / CI workflow。

## 设计合理性：做得好的地方

### 1. 与 Agent OS 不可协商原则对齐

医疗设计把模型放在不可信推理位置：医生签发是独立业务事务，模型没有签发工具；
患者问答绑定已签发报告；学习候选不直接改生产。这与参考架构中的
“LLM proposes；trusted code authorizes and fulfills”、检索前授权、离线 gated
self-improvement、遥测默认无正文一致。

### 2. 产品边界清晰，避免过早承诺临床能力

- 默认场景收窄到成人 2 型糖尿病报告解释与医生辅助草稿。
- 仅合成病例、模拟医生、公开许可资料、本地开发。
- 明确禁止自动处方、自动改药、自主签发。
- 图片先做报告截图 OCR，关闭 CT/MRI、病理、皮肤临床诊断。
- 小样本实验通过 ≠ 临床有效性证明。

这些边界使“实验版可行”与“医疗产品可上线”被正确分开。

### 3. 数据与权限模型适合医疗审计

`Encounter` / `Evidence` 版本化、原始报告与医生确认事实分离、模型推测不得自动
成为事实、`SignedReport` 不可变、修订保留关系、患者每次读取重新授权、通知
outbox 不含诊断正文——这些是可审计医疗工作流的必要形状，也是工程可实现的。

### 4. Run 状态机与故障语义成熟

`UNKNOWN` attempt、租约 fencing、`state_version`、WAITING_BUDGET、证据版本冲突
导致旧 Run 过期、校验失败分类（缺证据 / 可修复格式 / 升级 / 权限立即停）都
直接对应真实生产事故模式。参考架构要求的 session/task/run 分离在此得到落地。

### 5. 预算与路由顺序正确

“授权 → 检索/上下文 → 路由 → 原子预留 → 调用 → 结算 → 保存 → 校验”避免了
常见反模式：先贵模型后兜底、把模型自报信心当路由依据、截断结果当完成、
usage 缺失当零费用。M3 先做基本阻断、M7 再做优化，顺序合理。

### 6. 实施计划可验收

M0–M9 的 Vxx 用例覆盖跨患者枚举、伪造角色、并发版本冲突、崩溃恢复、校验前
泄漏答案正文、报告修订竞态、预算并发超支、学习集泄漏等负面路径。这对医疗
系统比“happy path 演示”更重要。

### 7. 自建 Harness 偏离有充分理由

OpenClaw 官方信任模型明确：**一个 Gateway 一个信任边界**，不支持互不信任用户
共享同一 gateway/agent。医疗多角色（医生/患者/机构）、PHI、签发权威与租户隔离
要求更强的项目自有控制面。医疗设计“自建可信后端 + 直接模型适配器，不整体部署
外部 Harness”与该约束一致，同时仍复用 Hermes 会话/记忆分离与 DSH 调用控制点
思想——这是合理的产品级偏离，不是无依据的重写冲动。

## 可行性评估

### A. 架构可行性：高

组件清单（Policy / Privacy / Knowledge / RunStore / Budget / Router /
ModelProvider / AnswerValidator / Report / Speech / Evaluation / Release）与
参考架构五平面映射清楚。首版单流程执行者、PostgreSQL 任务表、API 与 worker
分离，避免过早引入多智能体编排或消息集群，复杂度可控。

### B. 合成文本 MVP（M1–M5）：中高可行

前置条件：

1. M0 ADR 固定 Python/TS 框架、状态 schema、模拟 ModelProvider、目录与迁移。
2. 建立 `make check` 与 CI（当前仓库缺失，设计已点名）。
3. 50–100 条**人工编写**合成评测，覆盖辅助草稿、报告解释、证据不足、越权。
4. PMC 连接器用官方 API + mock HTTP 双路径，不把网页爬取当获取策略。

在以上条件下，文本闭环（医生证据 → 草稿 → 校验 → 签发 → 患者问答）可在有限
工程周期内交付演示级系统。主要不确定性在 **AnswerValidator 的临床规则内容**
与 **引用支持率评测标准**，而不是 HTTP/API/数据库本身。

### C. OCR / 语音（M6）：有条件可行

工程路径成熟（文件扫描、OCR、STT/TTS 适配器）。医疗可行性取决于：

- 数字、单位、否定词、时间字段的逐项确认 UI；
- 医学实体错误率门槛由临床负责人预先批准；
- 外部 STT/TTS 的数据处理协议与驻留；
- 未达标能力保持关闭。

设计已写明这些条件；若跳过确认或门槛，则不可接受。

### D. 成本优化路由（M7）：有条件可行

事务型预算账本、未知用量阻断、跨模型重建结构化上下文在工程上可行。是否
“更省钱且不降质量”是实证问题。设计正确要求：没有测出优势也记录真实结果，
不降低质量门槛凑数。

### E. 学习与发布（M8）：方向可行，治理难度中等

候选 → 授权去标识 → 留出集 → 审核 → 影子 → 小范围发布 → 回滚 的流水线与
RRSI/Hermes 学习闭环的正确用法一致（离线、有门禁）。难点是：

- 医生修订不是真值；
- 错误/恶意反馈隔离；
- 同患者/事件族防泄漏；
- 紧急撤权优先于版本固定。

这些在文档中已识别，需要在实现前写成可执行策略与测试，而不是口号。

### F. 真实患者试点：当前不可行（设计已正确门禁）

未完成部署地区、真实授权、机构规则、临床负责人、数据处理与监管适用性 ADR
之前，环境开关必须阻止真实患者模式。此判断与 WHO 多模态治理强调的监督/
评估背景一致，也符合仓库隐私红线。

## 与参考架构的一致性检查

| 参考架构要求 | 医疗设计 | 结果 |
| --- | --- | --- |
| Session / Task / Run 分离 | Encounter + Run + 证据版本；会话连续性不承担耐久工作 | 一致 |
| 调度与耐久执行分离 | API 与 worker 分离；租约与检查点 | 一致 |
| Privacy Gateway + Token Vault + Fulfillment | 明确模块；签发与副作用在可信后端 | 一致 |
| 检索前 ACL | KnowledgeService 授权检索；DB 查询不发患者原文 | 一致 |
| 记忆/技能候选制与离线门禁 | LearningCandidate + AgentRelease + 留出集 | 一致 |
| 遥测默认无正文 | 日志/审计用不透明引用 | 一致 |
| OpenClaw 作可替换外壳 | 医疗实验改为自建 Harness | **有意偏离**；需文档层正式接受 |
| 开放决策（语言/库/租户等） | 推到 M0 ADR | 正确推迟，但阻塞实现启动 |
